# C89 uxn/Varvara emulator — design

Date: 2026-11-08
Status: draft for approval

## Intent

Write our own uxn/Varvara emulator instead of borrowing one. The first
milestone is that it runs **Left** (the Varvara text editor) well enough to
use it: open, edit, save, browse directories.

The deeper aim is **portability of the CPU core**. The user wants to be able
to take the core and drop it into a DOS program or an embedded device
without editing it. That is why it is written in C89. The desktop host that
runs Left is a separate, modern layer built on SDL3, with a Dear ImGui
debugger (via cimgui).

The repo's existing Python emulator (`src/uxnemu.py`) is not a reference:
an audit found it implements the pre-2022 opcode table and has many semantic
bugs. Do not port from it.

**Reference implementation (user's decision):** the reference uxn C emulator
(git.sr.ht/~rabbits/uxn, MIT) may be read freely to settle behaviour,
especially where the wiki is thin (screen sprite drawing, file stat and
listing formats, console argument delivery, the order of short-mode device
calls). We write our own code. Where the wiki and the reference disagree,
**the reference wins**, so a mismatch against reference-derived tests is a
bug in our emulator.

**Offline builds (user's decision):** a fresh clone must build on a new
laptop with no internet access. Everything the build needs is in the repo as
source.

## Goals

1. A **portable uxn CPU core** in strict, freestanding C89.
2. **Varvara devices** sufficient to run Left: System, Console, Screen,
   Controller (keyboard), Mouse, File, Datetime.
3. An **SDL3 desktop host** that shows the Varvara screen and feeds input.
4. A **cimgui debugger** window that can be toggled on and off.
5. Built with **nob.h**; SDL3, cimgui/Dear ImGui and nob.h **vendored** so a
   fresh clone builds with just a compiler.
6. A **test suite** that checks the core against a current reference uxn
   implementation.

## Non-goals (for this version)

- Audio device, gamepad support.
- Actually shipping a DOS or embedded port. The core must be *ready* for
  them; doing the port is later work.
- Fixing or replacing the Python toolchain in `src/`.
- Running the SDL3/cimgui host on old machines. Only the core targets old
  hardware.

## Anti-goals (would be a failure even if Left runs)

- The core includes any libc header, uses globals, allocates memory, or uses
  C99 features. If porting the core to DOS or a microcontroller needs edits to
  core source, the design has failed.
- Implementing the old opcode table or old-spec behaviour. Current spec only.
- A build that needs anything beyond a C/C++ compiler, CMake + Ninja (for
  SDL3 only) and what's in the repo: no package manager, no network,
  including for the tests.

## Constraints

- **Toolchain on this machine (verified):** clang 22.1.4 targeting
  x86_64-pc-windows-msvc (C and C++ both compile and link; VS 2019/2022 libs
  present), tcc 0.9.27, cmake 4.3.2, ninja 1.13.2. No gcc, no MSVC `cl` on
  PATH. CMake is allowed **only for building SDL3** (user's decision); our
  own code builds through nob alone.
- **Repo conventions:** each experiment lives in its own top-level folder.
  Commit directly to `master`; no feature branches.
- **Licensing:** the repo is public and MIT. Vendored code must keep its own
  license files (SDL3: zlib; Dear ImGui and cimgui: MIT; nob.h: as shipped).
  No code copied from projects without a permissive license (e.g. uxn32's
  `uxn32.c` is "all rights reserved" — do not copy from it).

## Architecture

Three layers, with dependencies only pointing downward:

```
emu/
  core/      uxn CPU: strict freestanding C89, no dependencies
  varvara/   Varvara devices: C89 + libc, no SDL
  host/      SDL3 window, input, rendering, cimgui debugger (C99 / C++ for imgui)
  tests/     test ROM sources, expected outputs, test runner
  vendor/    SDL3, cimgui (+ Dear ImGui), nob.h — each with its LICENSE
  nob.c      build script
```

Everything lives under `emu/`, following the repo's one-folder-per-project
convention. *(My call; the conversation sketched `vendor/` and `nob.c` at the
repo root.)*

### Layer 1: the core (`emu/core/uxn.h`, `emu/core/uxn.c`)

**Language rules** — enforced by the build, not just by convention:

- ISO C89: compiles clean with `clang -std=c89 -pedantic -Wall -Wextra
  -Werror` and with tcc.
- **Freestanding:** includes no headers at all (not even `<stddef.h>`), calls
  no libc functions. Verified by compiling the core with `-ffreestanding` and
  checking the object has no undefined symbols.
- No `//` comments, no `stdint.h`, no `long long`, no `inline`, no mixed
  declarations, no VLAs, no floating point.
- Never assumes `int` is wider than 16 bits. Anything that can exceed 16
  bits (e.g. the step counter) uses `unsigned long`.
- Never assumes `unsigned char` is exactly 8 bits or `unsigned short` exactly
  16: every byte result is masked `& 0xff`, every short `& 0xffff`.
- **Endian-independent:** shorts are always assembled from two bytes,
  big-endian as uxn requires. No type-punning, no casting byte pointers to
  short pointers.
- **No global or static mutable state.** All state is in a host-owned
  struct, so several machines can run side by side.

**Types** (prefixed to avoid colliding with SDL's `Uint8`/`Uint16`):

```c
typedef unsigned char  ux_u8;   /* masked to 8 bits */
typedef unsigned short ux_u16;  /* masked to 16 bits */
```

**Machine state, owned by the host:**

```c
typedef struct UxStack { ux_u8 dat[256]; ux_u8 ptr; } UxStack;

typedef struct Uxn {
    ux_u8   *ram;        /* 65536 bytes, supplied by the host */
    UxStack  wst, rst;   /* working and return stacks */
    ux_u8    dev[256];   /* device port memory */
    ux_u8  (*dei)(struct Uxn *u, ux_u8 port);
    void   (*deo)(struct Uxn *u, ux_u8 port);
    void    *user;       /* host context */
    ux_u16   pc;         /* resume point after a step-limited run */
    ux_u8    fault;      /* nonzero if halted by an error */
} Uxn;
```

The core never allocates. RAM is a pointer because a 16-bit DOS compiler
cannot declare a 65536-byte object and many microcontrollers keep the ROM in
flash; the host decides where memory comes from.

**Memory access macros.** Every RAM read/write in the core goes through
`UXN_PEEK(u, addr)` / `UXN_POKE(u, addr, val)`, defaulting to `u->ram[addr]`.
A port can predefine them (before including `uxn.c`) for far pointers,
paging, or flash-backed reads, without editing the core. Same idea for
division: `UXN_DIV(a, b)` defaults to `/`, for chips without a hardware
divider.

**Execution API:**

```c
/* Run from pc until BRK, a fault, or max_steps instructions.
   max_steps == 0 means no limit. */
int uxn_eval(Uxn *u, ux_u16 pc, unsigned long max_steps);
/* returns UXN_BRK, UXN_LIMIT (u->pc holds where to resume), or UXN_FAULT */
```

The step limit lets an embedded main loop or interrupt handler keep control,
and lets the debugger single-step (`max_steps == 1`).

**Faults** *(my call)*: the CPU itself never faults under the current spec,
since stacks wrap and division by zero gives 0. `u->fault` is set only by the
host, inside a `dei`/`deo` callback (System halt, or a host-side error). The
core checks it after every device call and returns `UXN_FAULT` if it's
nonzero. There is no stack overflow or underflow detection; the debugger
stops on breakpoints, step limits and halts.

**Semantics:** the current uxn specification (the uxntal opcode reference on
wiki.xxiivv.com), including:

- The current opcode order (`BRK INC POP NIP SWP ROT DUP OVR EQU NEQ GTH LTH
  JMP JCN JSR STH LDZ STZ LDR STR LDA STA DEI DEO ADD SUB MUL DIV AND ORA EOR
  SFT`) with short (2), return (r) and keep (k) modes.
- The immediate opcodes `JCI`/`JMI`/`JSI` (0x20/0x40/0x60) and `LIT`/`LIT2`
  and their `r` variants.
- 256-byte stacks whose pointers wrap. RAM addresses and PC wrap at 0x10000.
- Division by zero gives 0.
- Device access goes through `dei`/`deo` with `dev[]` holding port values,
  short-mode device ops touching port and port+1.

Whatever the current spec says wins over this list.

### Layer 2: Varvara devices (`emu/varvara/`)

Plain C89 with libc allowed, no SDL. It implements device behaviour against
an abstract host interface (framebuffer memory, input events, file system
calls, clock). Devices for this version:

| Device | Port | Needed for Left |
|---|---|---|
| System | 0x00 | vectors, palette, halt (0x0f), expansion (memory copy/fill), metadata, debug |
| Console | 0x10 | stdin/stdout/stderr, argument passing to the ROM |
| Screen | 0x20 | two 2bpp layers, pixel/sprite/auto ports, resizable size, palette from System |
| Controller | 0x80 | keyboard buttons and key characters |
| Mouse | 0x90 | position, buttons, scroll |
| File | 0xa0, 0xb0 | read/write/append/delete/stat, directory listing in the spec's format |
| Datetime | 0xc0 | local time |

Follow the current Varvara device spec on wiki.xxiivv.com for exact
behaviour.

**File paths** *(my call)*: relative paths resolve against the process's
working directory, as in the reference emulator, and by default there is no
confinement, so Left can browse up through `..` and open whatever the user
points it at. An optional `--root DIR` flag confines both reads and writes to
`DIR` and its subdirectories, for running ROMs you don't trust.

Varvara is in its own layer because file and datetime need libc, which the
core must not have, and because a DOS port could reuse it with a different
host.

### Layer 3: SDL3 host and cimgui debugger (`emu/host/`)

Modern machines only. It may use C99 (SDL3's headers need it). Dear ImGui is
C++ and is compiled with clang++; our own host code stays C and talks to
imgui through cimgui.

- **Window:** shows the Varvara screen through an SDL_Renderer streaming
  texture, at 1×/2×/3× zoom. With the debugger hidden, it looks like the
  reference emulator.
- **Timing:** screen vector at 60 Hz. Each frame runs with a step limit, so a
  runaway ROM cannot freeze the UI.
- **Input:** SDL keyboard/mouse events mapped to Controller and Mouse.
- **Launch:** `emu path/to/rom.rom [args…]`, plus a File → Open ROM menu
  item.
- **Debugger toggle: Right Ctrl** (user's decision; their keyboard is a 60%
  Ducky One 2 Mini, so no function keys and nothing that needs Fn). Right Ctrl
  is reserved for the emulator and never reaches the ROM; only Left Ctrl maps
  to Controller button A. Tab is passed through to the ROM as usual (Left
  needs it for indenting).
- **Debugger**, using imgui's SDL3 and
  SDL_Renderer backends:
  - CPU: PC, working stack, return stack; pause, step, step over, continue,
    reset.
  - Disassembly around the PC; click a line to set or clear a breakpoint.
  - Memory: hex view of RAM and the 256 device-port bytes, with Varvara port
    names.
  - Console: the ROM's stdout/stderr output.
  - Menu: open ROM, reload, zoom.

## Vendoring

Everything in `emu/vendor/<name>/`, each with its upstream LICENSE and a
`VERSION` (or similar) file recording the upstream tag/commit.

- **nob.h** — single header.
- **cimgui** — the generated `cimgui.h`/`cimgui.cpp`, plus the Dear ImGui
  core sources it wraps, plus the SDL3 and SDL_Renderer backends.
- **SDL3** — **source**, a pinned release (user's decision: so a new laptop
  can build offline). Keep SDL's own CMake build files, `include/`, `src/`,
  the license and whatever else its CMake build needs. Tests, docs and IDE
  projects may be dropped to keep the repo small, as long as the CMake build
  still configures offline *(my call)*. SDL3 is built **with its own CMake
  build** (user's decision), which `nob.c` invokes: configure once into
  `emu/build/sdl3/` with the Ninja generator and clang, as a static library
  with SDL's tests and examples off, then link it into the emulator, so
  there's no DLL to copy *(my call)*. nob skips the CMake step when the
  static library is already built. Only Windows is required for this
  version; other platforms are left for later.
- **Test references** *(my call, follows from offline builds)*: the
  reference uxn source (MIT) and Left's source (MIT) are also vendored, under
  `emu/vendor/ref/`, so nob can build the reference assembler and CLI and
  assemble Left without the network.

## Build (`emu/nob.c`)

Standard nob bootstrap: `cc -o nob nob.c` once, then `./nob` rebuilds itself
when `nob.c` changes. Targets:

- the core, built **twice**: once as a freestanding strict-C89 check (clang
  `-std=c89 -pedantic -ffreestanding -Werror`, plus a tcc build), and once
  for real use;
- the test runner, run by `./nob test`;
- SDL3 as a static library, by running its CMake build (skipped when
  already built);
- the reference uxn assembler and CLI, plus Left, from `emu/vendor/ref/`, for
  the tests;
- the emulator executable, including compiling Dear ImGui and cimgui with
  clang++.

Outputs go to `emu/build/`, which is gitignored.

## Testing

- **Core opcode tests:** small test ROMs, one or more per opcode and mode,
  covering wrapping, keep mode, short mode, return mode, immediates and
  division by zero. Expected results come from a **current reference uxn**
  (assembler and CLI emulator), not from the copies in `C:\tools\uxn`, which
  date from May 2022 and predate the current opcode set. The test runner loads
  each ROM into our core and compares console output and final stack state
  with the reference.
- **Core portability checks:** the strict freestanding builds above. A
  16-bit-`int` build and a big-endian build can't run on this machine, so the
  code rules above stand in for them.
- **Varvara:** test ROMs for the file and datetime devices run in a headless
  mode (no window) of the emulator.
- **Acceptance:** a current build of Left, assembled from its upstream
  source, opens a file, edits it, saves it, and browses directories in our
  emulator.

## Left to the builder

- Exact source file split inside each layer and internal naming.
- How the Varvara layer's abstract host interface looks.
- The debugger's layout and its other shortcuts. They must work on a 60%
  keyboard without Fn, so no function keys, Insert, Page Up/Down, End or arrow
  keys. Prefer shortcuts that only act while the debugger has focus.
- Screen vector timing details and how frames are paced.
